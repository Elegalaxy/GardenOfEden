## Commands

```bash
npm run dev                 # Vite dev server
npm run build               # tsc -b && vite build
npm run typecheck           # tsc -b (three projects: app, node, harness)
npm run lint                # oxlint
npm test                    # vitest run (all tests)
npx vitest run tests/sim.test.ts               # one test file
npx vitest run -t "some test name"             # one test by name
npm run sim -- --seed a --ticks 5000 [--preset eden] [--every 500]   # headless run: tick, population, births, deaths by cause, food
npm run sim -- --seeds a,b,c --ticks 20000 [--warmup 1000]           # per-seed survey: final/min/max population, births, deaths by cause, lineage records kept / pruned
npm run sim -- --seeds a,b,c --ticks 20000 --no-family               # same, with parent-child knowledge sharing off (A/B); the last column `learned` counts shared memory entries
npm run sim -- --seed a --ticks 9000 --event drought@3000 --event plague@6000:48,32   # scripted world events, repeatable, also with --seeds (bounty@4000, meteor@5000:30,20)
```

## Architecture

A deterministic, seeded, god-style observation sim: bots wander a grid map, eat resource nodes and ruins, drink at water nodes, avoid danger, shelter, and reproduce on their own; the player watches and places nodes and bots. React 19 + Vite + TypeScript, Vitest, Canvas 2D for the map (`src/ui/render.ts`), SVG for the chart. Milestones M0-M15 are built (the MVP, trait inheritance, ruins, water and thirst, world events, save and load, family knowledge sharing, lineage records, long-run tuning, the simulation in a Web Worker, the family tree view, and heatmap overlays). The code is split into five layers under `src/`, and **`tests/architecture.test.ts` enforces the import rules** by scanning every source file (a file outside a layer also fails). When adding code, respect:

- `src/sim` — pure game rules. May import only other `src/sim` files (tests may also import `vitest`). Banned in non-test files: `Math.random`, `Date`, `performance.now`, `console`, browser storage, `process`, DOM globals/`fetch`, React, `node:*`. All randomness goes through the seeded named streams in `rng.ts` (`world`, `ai`, `birth`). Because sim files cannot import content, tests that need the real rules or presets live in `tests/`.
- `src/content` — data: `tuning.ts` (every behaviour number), `nodeDefs.ts`, `presets.ts`, assembled into `rules` in `index.ts`. May import sim types; no UI, persist, harness, or I/O.
- `src/harness` — Node CLI (`cli.ts`). Must not import `ui` or `persist`.
- `src/persist` — saves (M9). May import only sim types (not content), not ui/harness. `save.ts` is the versioned save format (`{version, seed, presetId, tick, hash, commands}`), `encodeSave`/`decodeSave` with strict validation and typed errors (never throws), `makeSave`; `share.ts` is the share link (base64url in the URL fragment `#run=`, capped at 12,000 characters); `autosave.ts` reads and writes the latest run through an injected storage object. Anything that needs content (does the preset exist, does the replay accept every command) is checked in `src/ui` at load time. Command key order inside a save must match the sim's (commands are part of the hashed state), so the decoder rebuilds each command from known fields in that order. Tests that need the real rules are in `tests/save.test.ts`.
- `src/ui` — React components, plus the simulation worker plumbing (see "Worker" below). Must not import `harness`. `store.ts` is the session (the page's mirror of the world, speed, tool, selection, async `dispatch(cmd)`, `clickMap`, `resetWorld`, and loading: async `exportSave`, `startLoad`, `cancelLoad`; the worker replays a load in slices through `replayJob.ts` and swaps the world in only when complete); `geometry.ts` (pixels/cells, picking), `tools.ts` (seven tools, keys 1-7 in button order, Esc = inspect), `labels.ts`, `chartMath.ts` and `traitMath.ts` are pure helpers (most with tests); the header holds `RunMenu`, a floating "Run & save" panel (closed by default, forced open while a load runs, results as a toast when shut) around `RunPanel` (seed form) and `SavePanel` (`autosave.ts` keeps the latest run in localStorage, `shareLink.ts` loads a `#run=` link, `download.ts` saves a file); the other panels are `Toolbar` (the tool buttons and the 1-7/Esc/D/B/P/M keys) with `ToolStatus` (hint and notice, rendered under the map), `Inspector`, `StatsStrip`, `PopulationChart`, `TraitChart`, `TraitSummary`, `DeathCauses`, `EventLog` (Depleted filter off by default), around `WorldCanvas` (draws via `render.ts`; takes children drawn over the map, used for the empty-world note). `FamilyPanel` (M14, in the side column below the Inspector: ancestors chain, descendants tree, founder lines; pure `familyMath.ts` for rows, wording, indentation caps and tree keys; `familyFocus.ts` for which record it shows, an override that holds only while the map selection is the one it was made for; `useFamilyData.ts` for the throttled, stale-safe `queryFamily`/`queryFounders` calls; the Inspector's "Show family tree" button calls `revealFamily`; it reads lineage through the worker, never the page's `ViewWorld`; HTML lists for keyboard use, fixed-height scrolling tree box so refreshes move nothing), `EventsPanel` (the four world-event cards and the in-progress list) and `eventInfo.ts` (their text, keys D B P M, blocked reasons) sit under the map; plague and meteor are map tools (`tools.ts` `EVENT_TOOLS`). `HeatLegend` (M15, a panel in its own grid area `heat` under the map's status line: layer None/Traffic/Births/Deaths and range All time/Recent as radio groups, key H cycles the layer, the numeric legend, and the "Under cursor" readout from `hoverCell` in the store) controls the heatmap overlay that `render.ts` draws under the nodes (`heatRender.ts`); `heat.ts` is the pure side (grid, `observeWorld`, snapshots, bins, legend text; see "Heatmaps" below); `typing.ts` is the shared "typing in a field" check for the key shortcuts. Styles: `styles.css` (base) and `panels.css`.

  **Layout rules (keep them when touching the UI):** `.workspace` in `panels.css` is a grid with named areas per breakpoint (phone: map, status, speed, tools, stats, panels; 901px: main column plus a 360px side column; 1100px: tools become a rail left of the map). The map must fit the first screen at 1280x800 with the controls and tools: `.map-frame` is capped by `--map-chrome` (the height of everything else, set per layout), so adjust that number if you add or remove rows above or below the map. The side column (`.area-side`) spans every grid row and has `contain: size` so a tall side column (selected bot's inspector, family tree, log) spills below instead of stretching the rows and pushing the map down; keep that if you add side panels. Anything that appears or changes while playing (hint, notice, toast, menu, event chips, the empty-world note) must not change the height of anything in flow: reserve its space or float it over the page. The map frame uses `box-shadow`, not a border, so the canvas fills the box it was measured from. Chart x ticks come from `xAxisTicks` (`chartMath.ts`), never a fixed count. Keep every button at least 44px tall. Verify layout changes by measuring (`getBoundingClientRect`) at 1280x800, 1440x900, 1024x768, 768x1024, 375x812 and about 290px wide, including before/after switching tools and placing things.
- `src/main.tsx` is the app entry (not a layer). Nothing may import from the sibling `rpg/` or `trading-sim/` projects.

### Worker (M13)

The sim runs in a Web Worker; the page only draws and sends messages. **Logic lives in `src/ui/simHost.ts`** (pure, DOM-free, Vitest drives it directly): `createSimHost()` owns the `World`, the load (replay) job and, from M15, the heat grid, and exposes `handle(msg): FromWorker[]` and `pumpLoad()`; `createHostRunner()` wires it to a `post` function and a scheduler. `sim.worker.ts` is a thin adapter around the runner (do not add the `webworker` lib to tsconfig; `self` is typed locally). `simClient.ts` has `createWorkerClient()` (falls back to inline, with a notice, if `Worker` is missing or fails before `ready`) and `createInlineClient()` (same host on the page's thread, `structuredClone` on every message; tests use it). `protocol.ts` holds the messages (`advance`, `command`, `reset`, `load`, `cancelLoad`, `exportSave`, `select`, `query`, `heat{layer|null, range}`, `sync`; and `frame`, `commandResult`, `loadProgress`, `loadDone`, `save`, `queryResult`, `synced`, `error`, `ready`, `heatSnapshot`). Messages are handled in order, so a command is recorded at the right tick. The page keeps a `ViewWorld` (`viewWorld.ts`, `applyFrame`): per-tick data every frame (tick, nodes, bots without memory as `ViewBot`, events, totals) and slow data (samples, log, commands, the selected bot with memory) at most about 4 times a second, when paused, and after commands, selections, resets and loads. Panels and render/geometry helpers take a `ViewWorld`, never a `World`; anything the mirror lacks must come as a frame field or a `query`, not by sending the whole world. `loop.ts`/`planFrame` stay on the page and keep one `advance` in flight (ticks pile up, capped at 200). In `src/sim`, helpers that the page also calls (`checkCommand`, `takeSample`, `totalFood`, `traitStats`, ...) take a `Pick` of the fields they read; keep it that way when adding such a helper. Tests wait for answers with `settled()` from `store.ts`. The worker must change no behaviour: `npm run sim -- --seeds a,b,c --ticks 20000 --warmup 1000` before and after must match.

### Heatmaps (M15)

Heat lives outside the `World`, in a `HeatGrid` (`src/ui/heat.ts`, 96 x 64 cells; per layer `traffic`/`births`/`deaths` an all-time `Float64Array` and a `recent` `Float32Array` that fades by 0.9 every 100 ticks). The `SimHost` owns it and calls `observeWorld(heat, world)` after every `step` and after every applied command (a meteor kills at command time); `createReplayJob`'s `onTick` hook calls the same observer after every step and applied command, so a load rebuilds the grid exactly (a load builds its own grid and swaps it in only when complete; a failed or cancelled load keeps the old one). It is not hashed and not saved (`src/persist` unchanged). Traffic is +1 per living bot per tick; births and deaths are the change in `totalBirths` / the death total, attributed from the newest matching `World.log` entries (they carry x and y; events that fell out of the 500-event ring are counted in `unattributed`, never put in a wrong cell). Display constants live in `heat.ts`, not `tuning.ts`. The grid is always accumulated; the page only gets a `heatSnapshot` (one layer as a `Float32Array` plus `max`, `hottest`, `total`, `runId`) while a layer is on: after a `heat` request, a command, a reset, a load, with every slow advance (paused) and otherwise at most about 4 Hz (`HEAT_INTERVAL_MS`). The store keeps `heatLayer`, `heatRange` and the latest matching `heat` snapshot (`WorldSnapshot`), and `hoverCell` in a separate small store (`useHoverCell`) so pointer moves do not wake every panel. `render.ts` draws the layer right after the grid through `heatRender.ts` (offscreen canvas, one pixel per cell, rebuilt once per snapshot; one neutral warm-white ramp of five steps; square-root scale for traffic, linear for births and deaths). Key H cycles None, Traffic, Births, Deaths (ignored while typing); it must not clash with 1-7, Esc, D, B, P, M. The panel reserves its height (the body's minimum height is set per breakpoint in `panels.css`; re-measure it if the legend text changes) so switching layers never moves the page, and it sits below the map so `--map-chrome` is unchanged. Tests: `heat.test.ts` (pure), `simHostHeat.test.ts` (host, including save then load giving a bit-identical grid), `heatRender.test.ts`, `storeHeat.test.ts`.

### Sim flow

`createWorld(seed, preset, rules)` builds a `World` (plain JSON). `step(world, rules)` advances one tick in place; `rules = { tuning, nodeDefs }` comes from `src/content`. Player commands (`commands.ts`: `applyCommand`, `checkCommand`) change the world between ticks and are recorded in `world.commands` with their tick; `replay.ts` rebuilds a run from seed + commands (same `stateHash` as the live run). `stats.ts` reads the samples (window changes, per-minute rates, trait drift; a minute is `tuning.stats.minuteTicks` ticks). Per tick, bots act in id order: perceive -> memory -> decide -> act -> metabolise -> death check, then a reproduction check for survivors. After the loop, in this order: dead bots are removed, children are spawned (`birth` stream), the lineage store is pruned if over its cap (`lineage.ts`), each dead bot leaves a ruin, resources regrow (times any drought or bounty), ruins decay (emptied ones are removed), expired world events and meteor craters are removed (`expireEvents`), then family knowledge is shared (`family.ts`), then a stats `Sample` is taken every `stats.sampleEvery` ticks. `step.ts` only orchestrates; the phases live in `perception.ts` (sense + memory), `brain.ts` (utility scores: flee, seekFood, seekWater, rest, reproduce, wander; `desperateFraction` makes a low-caution bot ignore danger avoidance at a higher hunger or thirst than a cautious one), `movement.ts` (greedy steering around remembered danger), `nodes.ts` (eat, drink, regrow, danger/shelter exposure), `ruins.ts` (leave, merge and decay ruins; a ruin inside a danger node decays `ruin.dangerDecayMult` times as fast), `metabolism.ts` (energy and thirst drain, damage, heal, age, death cause in the order danger or plague, thirst, starve, age) and `reproduction.ts`; `worldEvents.ts` holds the world events (below); `traits.ts` holds trait mutation, mean/min/max and the trait name order. `lineage.ts` (M11) keeps `World.lineage`, one compact `LineageRecord` per bot that ever lived (hooks: `createWorld`, `placeBot`, `spawnChildren`, both death sites; pruned past `tuning.lineage.maxRecords`, extinct branches first, never a living bot), plus the pure queries `familyView` and `founderLines`; it is bookkeeping only (no RNG, nothing reads it back), so it never changes behaviour. Bots interact through shared nodes, with one exception (M10, `family.ts`): a parent and its own child share memory. A newborn copies the shareable part of its parent's memory at conception (`family.inherit`), and a living parent and child within `family.shareRadius` cells swap memory on ticks that are a multiple of `family.shareEvery` (a radius of 0 turns exchange off). Only `family.shareKinds` pass (not ruins); an entry is copied only if the receiver lacks the node or has an older sighting, keeping its `seenTick` and `amount`, then `trimMemory` applies the usual caps. `MemoryEntry.learnedFrom` is the source bot id (null when the bot saw it itself; seeing the node again clears it) and `World.familyLearned` counts entries learned (survey column `learned`). Siblings and strangers never share (they only hear second-hand through a parent). No random draws; each bot checks only its own parent, in id order, so it is linear and deterministic. `tests/family.test.ts` covers it. `stateHash` (`hash.ts`) is the determinism check: same seed and same commands must give the same hash. World events (M8): the `triggerEvent` command (drought, bounty, plague, meteor; `worldEvents.ts`, numbers in `tuning.events`) is applied between ticks, recorded and replay-safe like any command, and draws no random numbers. `World.events` holds the timed ones (kind, start and end tick, centre, radius, magnitude copied from tuning at start); an event affects ticks T+1 to T+D and `expireEvents` removes it at the end of tick T+D. A drought or bounty multiplies resource regrowth (`regrowthMultiplier` in `nodes.ts`; both at once multiply). A plague adds `Exposure.plague` damage inside its disc in the bot's metabolise step; bots do not perceive it (deliberate, see GAME_DESIGN section 7). A meteor damages and kills at command time (cause `meteor`, ruin left) and leaves a crater, a `danger` node with `WorldNode.expires` set (0 means permanent; craters and ruins do not count against `player.maxNodes`). Death cause when health runs out: `plague` if plague damage that tick was larger than danger damage, else `danger`. Caps and duplicate refusals are in `checkEvent`. `tests/events.test.ts` covers each effect, refusals, replay, and runs scripted events on seeds a..e for 12,000 ticks (no extinction). Retune the events with `npm run sim -- --event ...`. `tests/tuning.test.ts` runs the eden preset for 20,000 ticks over seeds a..j (about 30 s) and checks the population never dies out, never explodes, and swings; re-run it after any tuning change. Children inherit traits with a seeded mutation (`tuning.mutation`: rate, strength, per-trait bounds; eight `birth` draws per child, after the three for placement). Each trait has a cost in `tuning.ts` (`senseDrain`, `metabolismSpeed`, `birthCost`); retune with `npm run sim -- --seeds ... --ticks 60000`, which prints final mean traits, and check traits do not all pin to their bounds. `tests/traits.test.ts` has the inheritance, cost and selection tests. Ruins (M7a): a node kind `ruin` (amount, `decay` per tick, removed at 0) made by the sim on every death; numbers in `tuning.ruin` and `nodeDefs.ruin`. Bots seek and eat them through the resource path (`isFood` in `perception.ts`, `eat` in `nodes.ts`); a ruin never regrows, so it is not retried once remembered empty. They use no RNG, are not logged, and do not count toward `player.maxNodes` (`placedNodeCount`); the player cannot place one (`checkCommand` refuses kind `ruin`) but can remove one. `world.eaten` totals food eaten per source, and the survey and CLI print `ruin%`. Resource depletions are not logged (the log holds births, deaths and commands). `tests/ruins.test.ts` covers ruins; any new code that switches on `NodeKind` must handle `ruin` and `water` (`exposureAt` and `regrow` must skip both). Water and thirst (M7b): a node kind `water` (a permanent spring: radius only, `amount` and `capacity` stay 0, nothing is taken when a bot drinks) and `Bot.thirst` (0 to `bot.maxThirst`). Thirst falls by `bot.thirstDrain` times `max(1, metabolism) ^ bot.thirstMetabolismPower` per tick (the steep power keeps a fast metabolism from out-breeding everything, and the floor at 1 keeps a slow one from pinning the lower bound; see the comment in `tuning.ts`); `drink` in `nodes.ts` refills it; at 0 the bot dies of cause `thirst`. `brain.ts` scores `seekWater` like `seekFood` (`thirstWeight`, `thirstyBelow`, `quenchedAbove`); `chooseWater` in `perception.ts` skips a spring inside a remembered danger unless the bot is desperate (thirst under `brain.desperateBelow`). Memory keeps water in its own slots (`memory.waterCap`, on top of `memory.cap`). Founders, placed bots and newborns start with full thirst. `DeathsByCause` has four keys, so anything that lists causes (UI, survey, CLI, test stubs) must include `thirst`. `tests/water.test.ts` covers water and thirst.

### Conventions

Unit tests sit next to source as `*.test.ts`. Files open with a short header comment explaining the module's rules; keep that style. Every number that changes behaviour belongs in `src/content/tuning.ts` or `nodeDefs.ts`, not in `src/sim`. Changing RNG draw order or the tick order changes every hash; treat that as a deliberate change.
